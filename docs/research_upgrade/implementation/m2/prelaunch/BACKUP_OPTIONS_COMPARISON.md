# B0-2 备份方案对比 — stock_research ~686GB @ PG16.13 (docker)

| 维度 | A 存储快照 | B pg_basebackup | C 关键表逻辑备份 |
|---|---|---|---|
| PG 一致性 | 需验证（卷快照≠一致性；需 fsfreeze/`pg_backup_start/stop` 配合） | ✅ 原生一致 | ✅ 表级一致（快照内） |
| 含 WAL | 取决于实现 | 需配归档才有 PITR，本身含启动所需 WAL | 不含 |
| 体量 | 686GB 卷级 | ~686GB 物理（可压缩 ~60-80%） | 单表 ~1-3GB 级 |
| 耗时 | 秒级（若支持） | 小时级（网络+IO，不承诺） | 分钟级 |
| 影响 | 低 | 中高 IO/CPU/网络 | 低 |
| 恢复粒度 | 全库 | 全库 + PITR（若归档） | 单表 |
| 可迁主机 | 依赖存储系统 | ✅ | ✅ |
| 前置 | 187 宿主访问（当前无 SSH 凭据） | `wal_level=replica`（已满足）+ 超级用户/REPLICATION 权限 + 归档配置（改 prod conf=独立审批） | 现有权限即可 |
| 当前可行 | **UNVERIFIED**——宿主机不可达 | 可做（无 PITR，恢复到备份点） | **可行** |

## 结论

- A：不可证——不纳入当前架构，留作宿主机访问开通后的升级选项；
- B：是全库灾难恢复唯一正确路径，但首次全量 + 归档启用都需要独立审批与资源窗口；归档参数修改属生产配置变更，**本轮不执行**；
- C：立即可做、成本最低，**只能保护声明的表**——T1/T4 前的"变更前保险"。
- **单表备份绝不能标注为 686GB 全库灾难恢复保障。**
