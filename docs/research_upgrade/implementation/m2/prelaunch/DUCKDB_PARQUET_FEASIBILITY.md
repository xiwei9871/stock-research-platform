# DuckDB/Parquet 冷热分层可行性（STORAGE-R1 P3）

评估对象：`market.stock_minute_bar` 全历史（default 分区 135GB + 36 个月度分区 ≈ 264GB 总量，~460M+ 行）与 `factor.factor_daily`（228GB，610.7M 行）。原则：**DuckDB 只作分析侧副本，永不替换生产 PG**；187 上不跑实验。

## 方案对比

| 方案 | 净节省 | 副本开销 | 查询性能 | 完整性 | 成本 |
|---|---|---|---|---|---|
| **S0 维持现状** | 0 | 0 | 现状基线 | 现状 | 0 |
| **S1 PG 内部优化**（bloat 回收+索引合理化，不改 schema） | 估 40–130GB | repack 期间 ~1×表空间 | **提升**（索引页密度恢复） | 全保留 | 需要腾挪空间，分阶段 |
| **S2 冻结分区 → Parquet + DuckDB 只读** | **估 180–240GB**（分钟线 2020–2025 段导出后 DROP 分区/迁移，需审批） | Parquet 副本 ~25–40GB（列存压缩比估 5–8×） | DuckDB 分析性能**通常优于** PG 行存（扫描型）；但需视图改写指向 parquet | PG 原数据在 NAS dump 可回滚；DROP 前双校验 | 导出管线 + 查询路由改造，工作量中 |
| **S3 PG + DuckDB 零复制**（postgres_fdw 外挂/duckdb pg 扩展读 PG） | 0（纯架构） | ~0 | 分析型快，点查仍走 PG | 全保留 | 部署复杂，收益有限 |

## 推荐：**S1 先行，S2 分段评估，S3 搁置**

- **S1 无条件先做**：索引膨胀修复 + 统计刷新是纯增益；恢复实例验证后分批执行。
- **S2 候选边界**：`stock_minute_bar` 2020–2023（default 分区 135GB）+ 2024 各月 —— 属"冻结历史"（不再写入）。导出 Parquet（按 year/month 分区）→ DuckDB/分析直接读；PG 侧仅在验证+审批后 DETACH+DROP。**先决**：① 恢复实例验证 parquet 行数/checksum 一致；② 确认消费方查询可路由（现有代码全部走 SQL，改造点明确但量大）；③ L2/后续 L2 代际覆盖被删窗口。
- **S3**：复杂度收益不成比例，不建议。
- `factor_daily` 属热写表（每日新增），**不适合** Parquet 导出；走 S1 索引治理。

## Parquet 导出估算（分钟线 2020–2023 default 分区）

| 项 | 估算 |
|---|---|
| 源 | 135GB PG heap+index，404M 行，列 ~8（时间/资产/OHLCV/freq） |
| Parquet zstd 后 | **估 15–25GB**（OHLCV float 列压缩极佳） |
| 净释放 | 135GB 分区 + 其分区索引 → **~135GB**（DROP 分区即刻，但需审批+备份覆盖） |
| DuckDB 查询 | 区间扫描/聚合预计 **快 3–10×**（列存+向量化）；单资产点查略慢于索引 |
| 导出成本 | COPY → parquet 一次性 ~1–2h（185/恢复实例上做，非 187） |

## 风险

- 查询路由改造是 S2 的主要成本与风险点——所有读 `stock_minute_bar` 的代码需支持"PG+Parquet 联邦视图"或显式切换；
- Parquet 无 MVCC/约束，只能承载**冻结数据**；
- 恢复能力依赖 NAS 备份代际，T4/恢复演练通过后才有底气做 DROP。
