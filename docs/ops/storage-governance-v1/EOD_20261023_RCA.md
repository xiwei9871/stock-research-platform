# EOD 发布失败根因分析 — 2026-10-23(及此前连续多日)

日期：2026-10-26 · 状态：根因已定位，修复方案待审
产物：`strategy_eod_publish_summary.json`(.failures/)、cron 日志、`platform_ready_build.host.log`、源码 `strategy_eod_publish.py`

## 0. 结论(TL;DR)

**这不是 10-23 单日事故，是长期存在的调度竞态(structural race)。**

`strategy-eod-publish`(launchd 20:30）的依赖等待闸只检查 `ops.daily_pipeline_status` 状态位；但发布函数额外要求 `factor.stock_score_daily`(score_version=manual_v1）当日行数——该数据由 **`platform_ready_build` 编排任务在 ~21:06-21:15 才写入**，永远晚于 pipeline READY 翻转时刻（~21:05)。

结果：20:30 的首次 EOD 运行**每晚必然失败**("base data checks did not all pass")，随后由 `platform_ready_build` 内部的 `strategy_daily_eod` step(21:22）或 22:17 自动修复运行**兜底成功**。`platform-ready-check`(21:30）恰好落在失败→成功之间，报 `external_sync_failed`——**陈旧/中间态信号，非同步通道故障**。

## 3. 为什么"以前能过"

publish 日志显示失败是**慢性常态**（成功零星分布，非 10-20 起新故障）。独立 20:30 EOD 的 wait 闸（看 status 标志）与 publish 闸（看实际行）标准不一致：只要 finalize 先翻 READY(21:0x）而 daily_factor 后写行（21:06+)，竞态必输。历史上零星成功对应上游偶尔早完成的窗口。

## 4. external_sync_failed 定性

21:30 ready-check 读取的是当时 EOD 状态（failed)——发布在 ~22:17 才由 build 兜底成功。**SSH/rsync/远端无故障**;10-23 数据完整并已发布（产物 +15 条复盘 + daily_review 包均在 `2026-10-23/` 与远端）。
