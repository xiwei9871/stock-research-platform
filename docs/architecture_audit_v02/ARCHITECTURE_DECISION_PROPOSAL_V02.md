# 架构决策建议 V0.2

**状态：`ARCHITECTURE_AUDIT_V02_COMPLETE / AWAITING_DESIGN_REVIEW / NO_PRODUCTION_CHANGES`**

基线 `9bd95562`。依据另外四份报告：CURRENT_STATE、DATA、RUNTIME、UIUX。本文中标为 DESIGN 的内容都是建议，不是已经做出的决定。

## 0. 总体判断

平台的基础已经具备：数据分层、带市场前缀的 `asset_id`、按交易所区分的规则引擎、证据和指纹体系、事务化的 EOD 发布、单一前端。

问题主要在三处：
- 已经有统一实现，但没有推广使用；
- 运行状态和通知没有用同一个键串起来；
- 研究结果没有以股票为中心组织。

这三处都可以通过"统一接口 + 逐步迁移"来解决，不需要重写，也不需要引入新组件。

## 1. 六个问题

### Q1 重复实现是否多于真正缺失的功能？

- **事实**：同一个基础问题被重复解决了很多次：
  - 日线读取有 59 个文件各自写 SQL；
  - "数据是否完整"的判定有 5 套阈值；
  - 涨跌停判断有 3 种规则（固定 9.5、固定 9.8/19.8/29.8、`tradeability`）；
  - 身份转换有 15 处，另有 39 份完全相同的 `_stock_code`；
  - ATR 有 3 种定义；
  - 通知有 5 条路径；
  - 研究或决策记录至少有 7 处。

  SOURCE_VERIFIED。
- **结构性问题**：已经存在的统一实现（`asset_identity`、`tradeability`、`atomic_json`、`ops.daily_pipeline_quality`、`is_tradable`）调用方很少。
- **不需要改的**：各策略的选股逻辑、CAP 的领域规则、四套 PIT 语义（它们各有用途，属于领域差异）。
- **最小整改**：每类基础问题只保留一个公共函数，新代码必须调用它，旧调用方按风险从高到低迁移：
  1. `core_data` 中存储的 `is_limit_up` 改为由 `tradeability` 计算；
  2. `dragon_case_library` 中错把北交所股票标成深市的问题；
  3. 生产 reader 改为调用 `load_daily_bars`；
  4. 就绪判定统一读取 `ops.daily_pipeline_quality`。
- **代价和风险**：每一项迁移都可能改变历史结果。必须做新旧结果对比，并在 PR 里说明差异。
- **待验证**：改变 `is_limit_up` 的存储口径会影响哪些下游，要先用 P1d 的差异清单评估。

### Q2 PostgreSQL 是否承担了明显不合理的负担？

- **事实**：数据库共 680 GB。其中 factor 271 GB、market 264 GB；`factor_daily` 占 228 GB，索引约 158 GB。人工研究状态（research、watchlist、ops 决策）只有约 1 GB。RUNTIME_VERIFIED
- **结构性问题**：
  - 体量主要来自可以重新计算的结果，以及同一组键的三份完整索引副本；
  - 冷数据没有生命周期管理；
  - 备份不区分数据角色，而且曾经写在数据库盘上。
- **不需要改的**：继续用 PG 作为主库；暂不引入 DuckDB。
- **最小整改**：
  1. 备份分层：人工状态加主数据每天做小 dump，全库备份写到其他盘；
  2. 在 185 恢复实例上测试 DATA 报告 §2 的方案 1 和方案 2；
  3. 只有分钟线冷分区可以考虑导出 Parquet，并在 PG 中删除。
- **待验证**：每种方案的真实收益。目前统计信息在崩溃恢复后被重置，不能用来判断索引是否在用，需要至少 2 周的使用统计。

### Q3 运行机制怎样最小化整合？

- **事实**：EOD 段已经有 manifest、status、事务提交、锁和依赖探针。另有 6 个状态家族，没有共享键。`run_id` 按日期固定生成，不是每次运行唯一；`code_version` 记录的不是 SHA；通知不带 `run_id`；数据库不可用时没有本地记录。
- **最小整改**：RUNTIME 报告 §3 的 R1–R5。全部基于 `ops.data_run_manifest`：放在 metadata 字段，加本地 `run_record.json`，上游各写一行，通知结果回写。不新增表。
- **代价**：小。
- **风险**：需要拿到 OpenClaw 的投递结果。目前只能从它自己的本地状态里读，没有回调接口。

### Q4 怎样让研究结果成为可查询、可跟踪的资产？

- **事实**：任何地方都查不到"谁、在什么时候、因为什么原因标记了这只股票"。观察池没有写入 API。个股页不读任何策略产物。CODE_VERIFIED
- **最小整改**：
  1. `lead_timeline(asset_id)` 只读聚合，即 RUNTIME 报告 §4 的方案 C，先接入 4 个已经入库的来源；
  2. `GET /api/assets/{id}/leads`；
  3. 观察池写入 API，只保留一个写入方。
- **不做**：不建统一线索表，不让所有模块写同一张表。
- **待验证**：CSV 类来源（各策略的每日 review）是否需要先入库才能高效查询。

### Q5 将来支持美股、加股，最大的迁移障碍是什么？

- **事实**：
  - `asset_id` 带 `CN:` 前缀，格式本身没问题。但有约 33 处 `split(":")`、私有的 `CN:` 拼接、约 70 处 6 位代码或 `zfill(6)` 假设，前端也有 `\d{6}` 和"6 开头即 SH"的判断。
  - 两套 asset_master：主用的 core 表没有 currency，却有 A 股板块布尔列和 3 个供应商代码列。
  - 交易日历用 `SSE`，资产表用 `SH`，两套交易所代码。
  - `LimitRule` 和成本约束没有 market 维度。
  - 财报表没有 currency 和财年字段。

  CODE_VERIFIED。
- **最大障碍**：股票身份的解析和交易所代码散落在各层（采集、策略、API、前端都有）。数据模型本身不是障碍。
- **现在必须做**：见 §5。
- **可以推迟**：FX、供应商代码映射表、合并两张主表、公司行为字段扩展、美加交易时段、issuer 主数据。

### Q6 React 平台怎样从功能集合变成研究工作台？

- **事实**：17 个导航项平铺；验证页展示的是 fixture 数据；估值已经计算但没有展示；股票代码不在 URL 里；出现回退时界面没有任何提示。
- **最小整改**：先做后端契约，见 UIUX 报告 §5 的三项：研究线索 API、统一的 `provenance` 块、观察池写入。前端只做四件事：
  1. 把 fixture 和回退数据标示出来；
  2. 股票代码写进 URL；
  3. 展示估值；
  4. 个股页增加一个"线索"标签页。
- **不做**：不重写前端；在完成上述四项之前不调整导航。

## 2. 方案对比

| 路线 | 内容 | 适用条件 | 结论 |
|---|---|---|---|
| A. 原地收敛（推荐） | 统一公共接口 + manifest 增量补充 + 线索只读聚合 + 备份分层 | 现在 | 采纳 |
| B. 新建平台层 | 新建 ResearchRun、AssetRegistry、Lead 表，引入编排框架 | 单人维护成本过高 | 不采纳 |
| C. 存储先行 | 先迁移 factor_daily、引入 DuckDB | 没有负载证据 | 推迟到负载测试之后 |

| 阶段 | 内容 | 前置条件 |
|---|---|---|
| 0 运行恢复 | 10-30 EOD 补跑；依赖锁；去掉 tushare 导入；交易日历告警；备份写到数据库盘以外，并加入调度 | Devin 正在处理 |

| 3 公共接口收敛（持续进行） | `parse_asset_id`、`load_daily_bars`、`is_limit_up` 改由 tradeability 计算、就绪判定统一 | 每项单独 PR，附新旧对比 |
| 4 存储验证 | 在 185 上测方案 1/2；分钟线冷分区 Parquet POC | 185 资源；PR #16 Gate C 不在同一窗口运行 |

## 4. 明确不做

新的任务管理系统、编排框架、微服务、新的 CAP、前端重写、物理合并 operator 表或 asset_master 表、因子宽表迁移、REINDEX、DuckDB 进入生产。

## 5. 多市场：现在必须改的公共契约

| 契约 | 改动 | 不改动的部分 |
|---|---|---|
| 身份解析 | `asset_identity.parse_asset_id() -> (market, exchange, symbol)`；每个市场一个代码校验器；加 lint 测试，禁止新增私有 `split(":")` | `asset_id` 字符串格式 |
| 交易所代码 | 统一成一套代码；交易所映射到（日历代码、时区、交易时段）的查找表 | 日历表结构 |
| 时间 | 交易日由日历给出，不用 `date.today()`；API 返回的时间戳必须带时区偏移；前端不再自行补 `+08:00` | 存储层的 date 列 |
| 规则键 | `LimitRule` 和成本约束增加 `market` 维度 | 规则内容 |
| 币种 | 主数据读取路径和 `finance.*` 增加 currency（可为空，默认 CNY） | 不做 FX |
