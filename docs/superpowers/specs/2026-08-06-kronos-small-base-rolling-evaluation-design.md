# Kronos small/base 日线滚动评估设计

## 1. 目标

建立一个可重复、无未来函数的 Kronos 日线预测评估实验，回答两个问题：

1. Kronos 是否比简单的持平基准更有预测价值；
2. 在完全相同的数据和滚动截止日下，Kronos-base 是否比 Kronos-small 更好。

本实验是研究评估，不直接改变个股工作台的线上默认模型，也不产生自动交易信号。

## 2. 固定实验口径

每次实验使用 20 只固定股票。股票代码通过参数或股票池文件传入，实验开始后不得根据预测结果更换股票。

默认参数如下：

| 参数 | 默认值 | 说明 |
|---|---:|---|
| `universe` | 20 只股票 | 固定股票池，可替换但必须记录版本 |
| `input_window` | 250 | 每个预测截止日前的最近 250 根日 K |
| `roll_step` | 1 个交易日 | 每个交易日滚动一次 |
| `evaluation_period` | 1 个月 | 起止日期可调，日期按交易日解释 |
| `forecast_horizon` | 10 | 每次预测未来 10 根日 K |
| `evaluation_horizons` | 1、3、5、10 | 分别评价未来第 1、3、5、10 日 |
| `sample_count` | 20 | 每个模型、每只股票、每个截止日生成 20 条采样路径 |
| `models` | `small`、`base` | 两个模型使用同一批输入快照 |

如果预测截止日在评估区间最后一天，则真实行情至少要准备到该截止日后的第 10 个交易日。预测所需的历史输入不足 250 根时，该样本标记为 `insufficient_input`，不得填充或向前复制数据。

## 3. 滚动测试定义

对每个测试股票和每个交易日 `D`：

1. 只读取 `D` 收盘时已经可获得的数据；
2. 取截至 `D` 的最近 250 根日 K 作为模型输入；
3. 生成未来 10 根日 K 的预测；
4. 使用 `D+1` 到 `D+10` 的真实日 K 计算评价指标；
5. 下一次将截止日推进到下一个交易日，重复以上流程。

日线价格口径与线上 Kronos 保持一致，使用现有日线数据和复权口径。small 与 base 必须接收完全相同的 OHLCV、时间戳、数据截止时间和输入行数。

测试结果以“股票 × 截止日 × 模型”为基本运行单元。一个月约有 20 个交易日、20 只股票，因此每个模型预计约 400 个预测起点；由于预测窗口重叠，汇总时不得把这些样本视为完全独立观测。

## 4. 模型对照方式

### 4.1 推荐执行方式：冻结快照后串行运行

由于 187 服务器当前 Kronos 服务一次只加载一个模型，采用以下顺序：

1. 先为整个月、20 只股票生成并保存所有历史输入快照；
2. 加载 `Kronos-small`，运行全部快照；
3. 记录模型版本、权重文件指纹、服务版本、设备、随机种子和推理耗时；
4. 切换服务加载 `Kronos-base`；
5. 使用同一批输入快照、同一组随机种子重新运行；
6. 对两个模型进行配对比较。

不能让两个模型在不同时间重新查询当前数据库作为历史输入，否则行情修复、复权更新或缓存变化可能破坏公平比较。

### 4.2 运行前检查

切换到每个模型后先执行单股票、单截止日的预检：

- 模型可以加载；
- GPU 显存没有溢出；
- 输出字段和时间戳完整；
- 20 条采样路径数量正确；
- 推理耗时可记录；
- 无效 OHLC、重复时间戳和 NaN 不进入正式结果。

预检失败只标记该模型为 `unavailable`，不能把模型加载失败误判为预测能力差。

### 4.3 缓存隔离

缓存键至少包含：

- 股票代码；
- 预测截止日；
- 输入指纹；
- 模型名称和权重指纹；
- 预测参数；
- 随机种子。

small 的缓存结果不能被 base 复用，反之亦然。实验运行优先使用独立研究结果目录，不覆盖个股工作台的线上预测缓存。

## 5. 评价指标

### 5.1 点预测

主要使用收盘价预测的 P50 作为点预测。对每个预测周期 `h ∈ {1,3,5,10}` 计算：

- 收盘收益误差：预测累计收益与真实累计收益的绝对误差；
- 归一化价格误差：`abs(predicted_close - actual_close) / last_close`；
- 方向准确率：预测收益和真实收益的正负方向是否一致；
- 上涨/下跌分别统计，避免总体胜率掩盖单边偏差。

### 5.2 概率预测

使用 P10、P50、P90 评价不确定性：

- P10–P90 对真实收盘价的覆盖率；
- 区间平均宽度；
- P10、P50、P90 的分位数损失；
- 实际价格是否频繁突破预测区间。

区间过宽并不代表预测好，因此覆盖率必须和区间宽度一起展示。

### 5.3 基准比较

至少保留两个不使用 Kronos 的基准：

1. 持平基准：未来收盘价等于截止日最后收盘价；
2. 简单漂移基准：使用最近若干日平均收益率外推。

最终报告同时展示：

- small 相对基准的改善；
- base 相对基准的改善；
- base 相对 small 的配对差异。

## 6. 模型选择判定

为了避免看完结果后再改变标准，实验开始前固定以下规则：

- 如果模型在主要误差指标上优于另一个模型，且配对差异的 95% 区间不跨越 0，同时预测区间覆盖率没有明显恶化，则标记为 `preferred`；
- 如果两个模型差异不稳定、不同周期各有胜负，标记为 `no_clear_winner`；
- 如果 Kronos 没有稳定优于简单基准，标记为 `not_proven`，不能仅凭某一只股票或某一天的结果宣称有效；
- base 即使准确率略高，如果显存、延迟或失败率明显更差，也要在结论中保留工程成本，不自动替换线上 small。

一个月窗口属于初步评估，不能作为最终长期稳定性结论。后续需要扩大到多个市场阶段和更长时间区间。

## 7. 数据与结果产物

每次实验生成一个不可变的实验目录，至少包括：

```text
experiment.json                  # 完整参数、代码版本、运行时间
universe.csv                     # 20 只股票及股票池版本
input_snapshots/                 # 每只股票、每个截止日的输入快照
run_manifest.csv                 # 每个运行单元的状态、模型和输入指纹
forecast_bars.parquet            # 预测 OHLCV、P10/P50/P90、代表路径
realized_bars.parquet            # 对应真实未来行情
metrics_by_stock_horizon.csv     # 股票 × 预测周期指标
metrics_by_model_horizon.csv     # 模型 × 预测周期汇总
model_comparison.csv             # small/base/基准的配对差异
report.md                        # 面向人工审阅的结论
```

`run_manifest.csv` 必须记录成功、数据不足、模型失败、接口超时等状态，不能只保存成功样本，否则会产生选择偏差。

## 8. 失败处理与数据质量

- 输入不足 250 根：标记 `insufficient_input`，不补数据；
- 未来真实行情不足：标记 `insufficient_truth`，不纳入对应 horizon 指标；
- 数据出现重复日期、NaN、非法 OHLC：标记 `invalid_input`，停止该运行单元；
- 模型或 GPU 失败：标记 `model_error`，保留错误信息和日志；
- 超时：记录实际耗时和超时原因，不自动 fallback 到另一个模型；
- 同一输入指纹重复运行：必须明确标记为缓存命中或强制重算；
- 任何一个模型失败，都不能用另一个模型的结果补齐比较结果。

## 9. 研究边界

本阶段不做以下事情：

- 不修改线上个股工作台默认模型；
- 不把预测结果写入交易策略或自动下单链路；
- 不使用未来真实行情参与输入或模型选择；
- 不用一次单票、单周期结果评价模型整体能力；
- 不因为 base 参数量更大就预先假设它一定优于 small。

## 10. 验收标准

实验实现完成后，至少满足：

1. 可通过参数指定股票池、测试起止日期、输入窗口、预测周期和模型列表；
2. 每个交易日、每只股票、每个模型都有明确运行状态；
3. small 和 base 使用相同输入快照，输入指纹可以核对；
4. 能输出 1/3/5/10 日的点预测、方向、误差和区间指标；
5. 能与两个简单基准比较；
6. 能单独报告模型加载失败、数据不足和超时，不将其混入准确率；
7. 能复现同一实验并得到一致的模型身份和输入口径；
8. 报告明确给出 `small_preferred`、`base_preferred`、`no_clear_winner` 或 `not_proven` 之一，并展示判定依据。
