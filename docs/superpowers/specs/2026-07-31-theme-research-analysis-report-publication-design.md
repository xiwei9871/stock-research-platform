# Theme Research Analysis Report Publication Design

## Status

Approved by the user on 2026-07-31.

The system generates long-running Theme Research analysis reports in the backend. The dashboard does not provide report-generation or report-upload controls. Generated Markdown, optional PDF, and a manifest are stored under a fixed report root. The application indexes those files in PostgreSQL, places each new immutable version into an admin review queue, and exposes it to all authenticated users only after an admin publishes it.

## Purpose

The existing Theme Research workspace restores and exposes the structured research for 25 themes: themes, industry-chain nodes, evidence, claims, and company mappings. It does not yet provide the durable narrative-analysis workflow previously used to analyze a theme and write a research report.

This design restores that capability without making users wait for long-running generation in the browser. It separates four responsibilities:

1. the backend research process performs research and creates report artifacts;
2. the report indexer validates and registers completed artifacts;
3. an admin reviews and publishes report versions;
4. authenticated users read or download published reports.

The report workflow is research-only. It must not alter scoring, signal, admission, watchlist, or trading behavior.

## Confirmed Product Decisions

- Reports are generated by the system in the backend, not manually generated in the dashboard.
- There is no frontend generate button and no frontend upload button.
- The canonical body is Markdown rendered as an online reading page.
- A PDF may be generated alongside the Markdown and offered as a download.
- Files live in a fixed server-side directory; PostgreSQL stores the searchable and reviewable index.
- Every generated version is immutable.
- A new version remains private while it is under review; the currently published version remains readable.
- Only `admin` accounts can preview pending reports, approve them, or reject them.
- After approval, the report is visible to all authenticated users.
- Historical published versions remain available.
- A manifest is required so the application never guesses identity or version from filenames alone.

## Non-goals

- interactive or synchronous report generation from the browser;
- report upload from the browser;
- editing Markdown in the dashboard;
- storing report bodies or PDF binaries inside PostgreSQL;
- publishing incomplete generation output;
- exposing server filesystem paths to clients;
- automatically publishing a report merely because generation succeeded;
- replacing structured Theme Research nodes, sources, claims, or company mappings with a narrative report;
- changing existing investment signals, scores, rankings, or admission gates.

## Architecture

Use a hybrid filesystem-and-database model.

### Filesystem: authoritative report artifacts

The backend generator writes one immutable directory per theme and report version:

```text
reports/theme-research/
  <theme_id>/
    <version>/
      report.md
      report.pdf        # optional
      manifest.json
```

The configured root must resolve beneath an explicitly configured report root. It must not be derived from user input or served as a static public directory.

The generator writes into a temporary sibling directory. It calculates checksums, writes the final manifest last, fsyncs as appropriate, and atomically renames the temporary directory to `<version>`. The indexer only reads finalized version directories. This prevents half-written Markdown or PDF files from entering review.

### PostgreSQL: authoritative publication index

Add a dedicated Theme Research report schema rather than extending `report.report_run`. The existing `report_run` entity is organized around `trade_date` and generic report types; it does not model theme identity, immutable versions, admin review, or a current published version.

The new database model stores metadata and relative paths only. It never duplicates Markdown or PDF content.

Suggested tables:

#### `theme_research_report_version`

- `report_version_id` text primary key;
- `theme_id` text foreign key to the authoritative Theme Research theme;
- `version` text;
- `title` text;
- `summary` text;
- `status` text: `pending_review`, `published`, `rejected`, or `archived`;
- `markdown_relative_path` text;
- `markdown_sha256` text;
- `pdf_relative_path` text nullable;
- `pdf_sha256` text nullable;
- `manifest_relative_path` text;
- `manifest_sha256` text;
- `generator_name` text;
- `generator_version` text;
- `generated_at` timestamptz;
- `indexed_at` timestamptz;
- `published_at` timestamptz nullable;
- `published_by_user_id` text nullable;
- `rejected_at` timestamptz nullable;
- `rejected_by_user_id` text nullable;
- `rejection_reason` text nullable;
- `row_version` bigint for optimistic concurrency;
- `metadata` jsonb for non-authoritative generator details;
- unique constraint on `(theme_id, version)`.

#### `theme_research_report_review_event`

- `event_id` text primary key;
- `report_version_id` text foreign key;
- `from_status` text nullable;
- `to_status` text;
- `actor_user_id` text;
- `comment` text;
- `request_id` text;
- `idempotency_key` text;
- `created_at` timestamptz;
- unique constraint on `(actor_user_id, idempotency_key)`.

The current report for a theme is the latest version in `published` state according to the publication transaction. An optional partial unique index may enforce at most one active `published` version per theme if old versions are transitioned to `archived`. In user-facing language, archived versions are historical published versions and remain readable.

## Manifest Contract

`manifest.json` is the handoff contract between the report generator and the application. A v1 manifest contains at least:

```json
{
  "schema_version": "theme_research_report_manifest_v1",
  "theme_id": "ai_power",
  "version": "2026-07-31.1",
  "title": "AI 电力主题分析报告",
  "summary": "报告摘要",
  "generated_at": "2026-07-31T10:00:00+08:00",
  "generator": {
    "name": "theme-research-report-pipeline",
    "version": "1.0.0"
  },
  "artifacts": {
    "markdown": {
      "path": "report.md",
      "sha256": "..."
    },
    "pdf": {
      "path": "report.pdf",
      "sha256": "..."
    }
  },
  "metadata": {}
}
```

The PDF entry is optional. Markdown is mandatory. Artifact paths must be relative, must remain inside the version directory after canonical resolution, and must name regular files rather than symlinks. Unknown fields are retained in metadata where safe, but an unknown `schema_version` is rejected.

## Indexing And Synchronization

Create a focused report index service. It runs once during application startup and then on a configurable interval. The same service is callable from an operational command for diagnosis and recovery, but it is not exposed as a user-facing generation or upload action.

For each finalized manifest, the indexer:

1. parses and validates the manifest schema;
2. resolves and validates all relative artifact paths beneath the configured root;
3. verifies that `theme_id` exists in the authoritative Theme Research database;
4. verifies Markdown presence and checksum;
5. verifies the PDF checksum when a PDF is declared;
6. derives a stable `report_version_id` from `theme_id` and `version`;
7. inserts a new `pending_review` row and its initial audit event;
8. treats an identical repeated scan as a no-op;
9. reports a conflict if an existing `(theme_id, version)` has different manifest or artifact checksums.

Indexing is additive and fail-closed. It never changes the publication status of an already indexed version and never overwrites an existing version with different bytes. A corrected report must use a new version identifier.

Synchronization diagnostics expose counts for discovered, indexed, unchanged, and invalid manifests plus bounded error details. Invalid artifacts remain on disk for operator diagnosis but do not enter the review queue.

## Lifecycle And State Transitions

The report state machine is:

```text
generated artifact -> pending_review -> published
                                  \-> rejected
published -> archived
```

Rules:

- Successful indexing creates `pending_review`; generation alone cannot publish.
- Only an authenticated user with `role=admin` may transition `pending_review` to `published` or `rejected`.
- Rejection requires a non-empty reason.
- Rejected content is not visible to normal users. The backend generator creates a new version after correction; it does not mutate or resubmit the rejected bytes.
- Publishing a version and archiving the previously published version for the same theme happen in one database transaction.
- Historical archived versions remain readable and downloadable because they were previously approved.
- Optimistic concurrency through `row_version` prevents two review screens from publishing or rejecting stale state.
- Review mutations require the existing session authentication, admin check, CSRF validation, request ID, and idempotency key conventions.

## Read And Review APIs

Add dedicated endpoints under the existing Theme Research namespace.

### Authenticated user reads

- `GET /api/research/theme-decomposition/themes/{theme_id}/reports`
  - returns current and historical approved metadata only;
  - does not disclose pending, rejected, absolute paths, or checksums.
- `GET /api/research/theme-decomposition/themes/{theme_id}/reports/{report_version_id}`
  - returns safe rendered-report metadata and Markdown-derived HTML for a published or archived version.
- `GET /api/research/theme-decomposition/themes/{theme_id}/reports/{report_version_id}/pdf`
  - authorizes the request, verifies the indexed file identity, and streams the PDF as an attachment;
  - returns 404 when no PDF exists.

### Admin review

- `GET /api/admin/theme-research/reports?status=pending_review`
  - lists report versions requiring review.
- `GET /api/admin/theme-research/reports/{report_version_id}`
  - returns pending report metadata and safe preview content.
- `POST /api/admin/theme-research/reports/{report_version_id}/publish`
  - requires expected row version, idempotency key, and optional comment.
- `POST /api/admin/theme-research/reports/{report_version_id}/reject`
  - requires expected row version, idempotency key, and rejection reason.

The API renders Markdown using a sanitizing renderer with raw HTML disabled or sanitized. Links receive safe attributes. The service reads only the exact indexed relative path, re-resolves it beneath the configured root, and may verify the stored checksum before serving. It never accepts a client-provided filesystem path.

## Dashboard Experience

### Theme list

Each theme may include a compact report indicator:

- `已发布` when a current approved version exists;
- `研究中` when no published report exists.

Pending-review state is admin-only and must not leak through the normal theme-list response.

### Theme detail

Add an `分析报告` area to the Theme Research detail workspace. It shows:

- title, summary, version, generation date, and publication date;
- an `在线阅读` action;
- a `下载 PDF` action only when a PDF exists;
- a historical-version selector containing approved versions only.

When no approved report exists, normal users see `分析报告正在研究中`. They do not see internal workflow state, rejected versions, filenames, or filesystem locations.

The report reading view uses the existing application shell and authentication state. It renders the Markdown as a readable article with headings, tables, citations, code blocks where present, and responsive typography. It does not embed a public static-file URL.

### Admin report review

Add `报告审核` to `ADMIN_NAV_ITEMS`, visible only when `currentUser.role === "admin"`. The page provides:

- pending report count and queue;
- theme, report title, version, generator, and generation time;
- sanitized Markdown preview;
- PDF download for comparison when available;
- `通过` and `驳回` actions;
- mandatory rejection-reason input;
- current row version and clear conflict feedback if another admin already acted.

There is no generate or upload control anywhere in this workflow. The existing generic `生成报告` workspace is outside this feature and must not be presented as the way to create Theme Research analysis reports.

## Authorization And Information Boundaries

- All report endpoints require an authenticated dashboard session when dashboard auth is enabled.
- Normal users may access only `published` and `archived` report versions.
- Admins may preview `pending_review` and `rejected` versions through admin endpoints.
- Review transitions require `role=admin`; frontend visibility is not a security boundary.
- Review mutations require CSRF validation.
- Absolute paths, filesystem roots, checksums, generator diagnostics, and rejection reasons are admin/operator data and are excluded from normal-user payloads.
- PDF and Markdown access is mediated by application endpoints, not by web-server directory exposure.
- Directory traversal, symlinks, special files, oversized manifests, unsupported encodings, and unsupported manifest versions are rejected.

## Error Handling And Operations

### Indexing errors

Invalid manifests are isolated per version so one bad report does not stop discovery of other reports. Diagnostics use stable error codes for:

- malformed or unsupported manifest;
- missing or unknown theme;
- missing Markdown;
- invalid or escaping path;
- checksum mismatch;
- declared PDF missing;
- duplicate version with different content;
- database unavailable.

The latest synchronization status and bounded recent errors should be visible through logs and an admin/operations diagnostic read model. Normal users receive no filesystem diagnostics.

### Serving errors

- Unknown or unauthorized versions return 404 to avoid disclosing private report existence.
- Missing optional PDF returns 404 while the Markdown report remains readable.
- An indexed file that later disappears or fails checksum returns a structured 503 and creates an operational error; it must not silently serve different bytes.
- Unsafe or unrenderable Markdown returns a controlled error page without breaking the application shell.

### Review errors

- Non-admin review attempts return 403.
- Missing CSRF returns 403.
- Invalid state transitions return 409.
- Stale `row_version` returns 409 with the current safe state.
- Rejection without a reason returns 400.
- Repeated requests with the same idempotency key return the original result.

## Configuration And Deployment

Add explicit settings for:

- Theme Research report root;
- index scan interval;
- maximum manifest size;
- maximum Markdown size;
- maximum PDF size;
- checksum verification policy when serving;
- Markdown renderer feature policy.

The production deployment mounts or preserves the report root independently from application release directories so a release does not delete research artifacts. The application process needs read-only filesystem access to finalized report artifacts; the generator needs write access. PostgreSQL remains the source of truth for review and publication state.

Rollout order:

1. deploy schema and report index service with serving disabled;
2. validate a small manifest fixture and production report-root permissions;
3. enable admin queue and review endpoints;
4. publish one canary report and verify normal-user isolation;
5. enable Theme Research list/detail report links;
6. index remaining generated reports;
7. retain rollback capability by disabling report routes without deleting artifacts or index rows.

### Frontend tests

- admin-only navigation and review queue;
- required rejection reason;
- conflict and failure states;
- explicit absence of generate and upload controls.

### End-to-end acceptance

1. Place a valid generated report directory under the configured root.
2. Confirm it appears only in the admin pending queue.
3. Confirm a normal account cannot discover or open it.
4. Publish it with an admin account.
5. Confirm all authenticated users can read Markdown and download the PDF.
6. Generate and index a second version.
7. Confirm the first version stays current during review.
8. Publish the second version and confirm it becomes current while the first remains in approved history.
9. Index malformed, escaping-path, and checksum-invalid fixtures and confirm none enter review.

## Success Criteria

- Backend generation is fully decoupled from browser request duration.
- The dashboard contains no Theme Research generate or upload button.
- Every valid generated report version reaches an admin review queue automatically.
- No pending or rejected report is visible to normal users.
- Admin publication makes the report available without application restart or manual file copying.
- A new pending version never replaces the current published version.
- Markdown is readable online and PDF is downloadable when present.
- Historical approved versions remain accessible.
- Repeated scans and repeated review requests are safe and idempotent.
- Filesystem paths and incomplete artifacts are never exposed to clients.
