# tech-bottleneck Data Readiness Audit Design

## Purpose

`tech-bottleneck-data-readiness-audit` is the pre-scoring gate for `tech-bottleneck-discovery`.

The command answers one question before any return test or bottleneck score:

> For an existing topN candidate pool, do we have enough structured and text evidence to evaluate each stock's bottleneck thesis?

It does not scan the full market, score expected returns, generate buy/sell instructions, or promote candidates. It only measures data completeness and identifies missing evidence.

## Position In Workflow

```text
Existing strategy topN candidate pool
-> tech-bottleneck-data-readiness-audit
-> ready_for_scoring / needs_evidence_backfill / data_blocked / source_gap
-> tech-bottleneck-discovery packet generation only for ready candidates
-> human review
```

This keeps candidate generation separate from evidence readiness. The audit can be run against any topN source: industry focus, mid-trend shadow candidates, strong-winner discovery, or a manually exported pool.

## Input

The first version uses a CSV candidate pool plus the existing Postgres database.

Required CSV column:

- `asset_id`

Recommended CSV columns:

- `stock_name`
- `trade_date`
- `candidate_source`
- `rank`

CLI options:

- `--candidates-csv`: path to the existing topN candidate file.
- `--as-of-date`: audit cutoff date. If omitted, use each row's `trade_date`; if that is missing, use the command run date.
- `--lookback-days`: evidence lookback window for report, event, and news text. Default: 365.
- `--output-dir`: artifact directory.
- `--run-id`: stable identifier for this audit run.
- `--service`: database service name. Default: `stock_research`.

## Data Sources

The first version reads only sources already available in `stock_research`.

### Strong Sources

- `core.industry_membership`
- `finance.main_business_composition`
- `research.stock_report_event`
- `research.stock_report_source`
- `research.stock_report_feature_daily`
- `event.institution_survey`
- `event.earnings_forecast`
- `event.earnings_express`

### Known Sparse Or Empty Sources

- `research.news_event_source`
- `research.news_event_mention`
- `research.news_feature_daily`

The news tables are part of the design because their emptiness is itself important readiness evidence. A pool can be marked with `source_gap` when a missing flag is caused by a system-level empty source rather than a single-stock absence.

### Not Yet Available As Structured Sources

- Patent tables
- Hiring or job posting tables
- Customer or supplier relationship tables
- Capacity expansion tables
- Product or technology taxonomy tables
- Structured chokepoint evidence tables

When these concepts are needed in v1, the audit uses text proxies and marks them as proxy evidence in the detail payload.

## Output

The command writes three artifacts.

### `readiness.csv`

One row per candidate:

- `run_id`
- `asset_id`
- `stock_name`
- `trade_date`
- `candidate_source`
- `rank`
- `as_of_date`
- `lookback_days`
- `has_industry_context`
- `has_product_revenue_exposure`
- `has_research_report`
- `has_bottleneck_keywords`
- `has_capacity_evidence`
- `has_customer_certification_evidence`
- `has_patent_or_technical_barrier`
- `has_news_or_announcement_catalyst`
- `has_invalidation_evidence`
- `coverage_score`
- `coverage_status`
- `missing_flags`
- `proxy_flags`
- `source_gap_flags`

### `readiness.json`

Structured details for review and debugging:

- Candidate identity
- Each coverage flag
- Evidence counts by source
- Up to three sample evidence snippets per flag
- Missing flag reasons
- Proxy-only flags
- Source-gap flags

### `summary.md`

A pool-level summary:

- Candidate count
- Coverage rate for each flag
- Status counts
- Top missing flags
- Systemic source gaps
- Ready candidate list
- Blocked candidate list

No per-stock research packet is generated by this audit. That belongs to `tech-bottleneck-discovery` after readiness passes.

## Coverage Flags

All flags are booleans. They are deliberately conservative: a weak text match can create a proxy flag, but it should not hide a missing structured source.

### `has_industry_context`

True when `core.industry_membership` has at least one valid row for the candidate on `as_of_date`:

```text
asset_id matches
start_date <= as_of_date
end_date is null or end_date >= as_of_date
```

Evidence detail stores `industry_system`, `industry_code`, `industry_name`, and `level`.

### `has_product_revenue_exposure`

True when `finance.main_business_composition` has a recent product-classified row:

```text
asset_id matches
report_period <= as_of_date
classify_type = '按产品分类'
item_name is present
```

Revenue fields are useful but not required because some rows can contain useful product names even when numeric revenue fields are sparse. Evidence detail stores the latest `report_period`, `item_name`, `revenue`, `revenue_ratio`, and `gross_margin`.

### `has_research_report`

True when any of the following exist within the lookback window:

- `research.stock_report_event`
- `research.stock_report_source` joined through `report_id`
- `research.stock_report_feature_daily` with `report_count_90d > 0` or `source_count > 0`

Evidence detail stores report title, report date, source type, broker, raw summary, company view, industry view, and risk summary when available.

### `has_bottleneck_keywords`

True when report, event, survey, or product text contains at least one bottleneck keyword.

Initial keyword groups:

- Chinese: `卡脖子`, `瓶颈`, `稀缺`, `国产替代`, `自主可控`, `关键材料`, `关键设备`, `核心零部件`, `供应链安全`, `受限`, `进口替代`
- English: `bottleneck`, `chokepoint`, `scarce`, `shortage`, `localization`, `substitution`, `critical material`, `critical equipment`

Evidence detail stores the source field and matching keyword. This flag can be based on product names, but such evidence is marked as proxy when no report or event text supports it.

### `has_capacity_evidence`

True when text evidence contains capacity or supply constraint language.

Initial keyword groups:

- `产能`, `扩产`, `爬坡`, `良率`, `交付周期`, `供给受限`, `供需缺口`, `满产`, `达产`, `建设周期`, `瓶颈产线`
- `capacity`, `ramp`, `yield`, `lead time`, `supply constraint`, `utilization`

Evidence detail stores the text source, keyword, and snippet.

### `has_customer_certification_evidence`

True when text evidence contains customer validation, qualification, order, or supplier-entry language.

Initial keyword groups:

- `客户认证`, `客户验证`, `导入`, `定点`, `合格供应商`, `供应商认证`, `批量供货`, `订单`, `在手订单`, `客户突破`
- `qualification`, `qualified supplier`, `design win`, `certification`, `customer validation`, `order backlog`

Evidence detail stores the text source, keyword, and snippet.

### `has_patent_or_technical_barrier`

True when text evidence contains patent, process, formula, equipment, or technical barrier language.

Initial keyword groups:

- `专利`, `技术壁垒`, `工艺壁垒`, `配方`, `know-how`, `核心技术`, `自研`, `高精度`, `高可靠`, `高纯`, `先进制程`
- `patent`, `process know-how`, `technical barrier`, `proprietary`, `high purity`, `advanced process`

Because there is no structured patent source in v1, this flag is marked in `proxy_flags` unless future data sources provide patent or IP records.

### `has_news_or_announcement_catalyst`

True when any of the following exists within the lookback window:

- `research.news_event_mention` joined to `research.news_event_source`
- `research.news_feature_daily` with nonzero news counts
- `event.earnings_forecast`
- `event.earnings_express`
- `event.institution_survey`

In v1, earnings and survey events count as announcement/event catalysts. If all news tables are empty, missing news catalyst evidence is also listed under `source_gap_flags`.

### `has_invalidation_evidence`

True when report, survey, news, or event text contains explicit contradiction or thesis-risk language.

Initial keyword groups:

- `降价`, `替代`, `需求不及预期`, `产能过剩`, `客户流失`, `毛利下滑`, `延期`, `减值`, `竞争加剧`, `路线变化`, `技术替代`
- `price cut`, `substitution`, `demand miss`, `oversupply`, `customer loss`, `margin pressure`, `delay`, `impairment`, `route change`

This flag is not a negative score by itself. It means the audit found data that can make the thesis falsifiable.

## Coverage Score

The score is a readiness score, not an alpha score.

```text
coverage_score =
  2 * has_industry_context
+ 2 * has_product_revenue_exposure
+ 2 * has_research_report
+ 1 * has_bottleneck_keywords
+ 1 * has_capacity_evidence
+ 1 * has_customer_certification_evidence
+ 1 * has_patent_or_technical_barrier
+ 1 * has_news_or_announcement_catalyst
+ 1 * has_invalidation_evidence
```

Maximum score: 12.

The three identity/evidence foundation flags carry higher weight because a bottleneck thesis should not be scored without industry, product exposure, and research/event context.

## Coverage Status

### `ready_for_scoring`

All of the following are true:

- `has_industry_context`
- `has_product_revenue_exposure`
- `has_research_report`
- `has_bottleneck_keywords`
- `coverage_score >= 7`

### `needs_evidence_backfill`

All foundation flags are true, but the candidate lacks enough bottleneck-specific evidence:

- `has_industry_context`
- `has_product_revenue_exposure`
- `has_research_report`
- not `ready_for_scoring`

### `data_blocked`

Any of the following are missing:

- `has_industry_context`
- `has_product_revenue_exposure`

These candidates should not receive a tech bottleneck score until identity and product exposure data are present.

### `source_gap`

The candidate is missing key evidence primarily because the underlying table is empty or systemically sparse for the whole run. In v1 this is most likely for news data.

`source_gap` is a status only when the candidate is not otherwise `data_blocked` and the missing source is material to the requested flags.

## Text Evidence Model

The audit builds a normalized in-memory text corpus per candidate from:

- report titles
- raw summaries
- industry views
- company views
- risk summaries
- institution survey summaries
- earnings forecast summaries
- news titles and content, when available
- product item names from main business composition

Each text record stores:

- `source_table`
- `source_id`
- `source_date`
- `field_name`
- `text`
- `proxy_only`

Keyword matching is case-insensitive for English and direct substring matching for Chinese. The first version intentionally avoids model-based inference; keyword evidence is auditable and deterministic.

## Error Handling

- Empty candidate CSV writes empty artifacts with a clear summary.
- Missing `asset_id` raises a CLI input error.
- Missing optional candidate columns are filled with empty values.
- Missing database tables raise an explicit error naming the table.
- Query failures fail the command; partial artifacts are not written.
- Unknown dates fall back to the run date only when neither row `trade_date` nor CLI `--as-of-date` is provided.

## Testing

Unit tests should cover:

- Empty candidate input.
- Industry membership date-window matching.
- Product exposure detection using `classify_type='按产品分类'`.
- Report detection using event/source/feature rows.
- Keyword flags across report, survey, earnings, news, and product text.
- Proxy flag behavior for patent/technical barrier evidence.
- News source-gap behavior when news tables are empty.
- Status transitions for `ready_for_scoring`, `needs_evidence_backfill`, `data_blocked`, and `source_gap`.
- Artifact writing for CSV, JSON, and Markdown summary.

Integration smoke should use a tiny candidate CSV against `service=stock_research` and verify the command writes artifacts without running return tests.

## Explicit Non-Goals

- No return, Sharpe, drawdown, or outcome testing.
- No full-market scan.
- No automatic score promotion.
- No LLM inference in v1.
- No browser or social-media scraping.
- No creation of new persistent database tables.
